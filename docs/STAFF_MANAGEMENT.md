# إدارة الحسابات الأولية والموظفين

هذا المستند يوثّق التعديل الإضافي على المرحلة الأولى: الإعداد الأولي لمرة واحدة،
وإدارة حسابات الموظفين، ومصفوفة الصلاحيات، والاختبارات، والمخاطر المتبقية.

## 1. الحسابات الأولية الثلاثة

يشغّل الإعداد الأولي **مرة واحدة فقط** وينشئ ثلاثة حسابات بالضبط:

| الحساب | الدور | المعرف الافتراضي | الغرض |
| --- | --- | --- | --- |
| المالك التجريبي | `SYSTEM_OWNER` | `owner-test` | اختبار معزول؛ لا يُدار عبر API |
| رئيس القسم | `HEAD_OF_DEPARTMENT` | `head1` | الصلاحيات الإدارية العليا الحالية |
| المقرر | `REGISTRAR` | `registrar1` | إدارة المحاضرين والمحاضرين التقنيين |

### طريقة التشغيل

```powershell
# 1) تأكد من أن PostgreSQL يعمل وأن DATABASE_URL مضبوط
#    (على الاستضافة: استخدم بيانات الاتصال التي يوفّرها المزوّد)

# 2) شغّل الإعداد الأولي (تم تنفيذه؛ يتوقف تلقائيًا إذا سبق التنفيذ)
pnpm --filter @attendance/api run setup:initial
```

يمكن تمرير كلمات المرور صراحةً بدلًا من توليدها:

```powershell
pnpm --filter @attendance/api run setup:initial -- `
  --owner-password "Owner-Strong-Pass-1!" `
  --head-password "Head-Strong-Pass-1!" `
  --registrar-password "Reg-Strong-Pass-1!"
```

يمكن أيضًا تخصيص المعرفات والأسماء:

```powershell
--owner-staff-id owner-test --owner-name "حساب المالك التجريبي"
--head-staff-id head1 --head-name "رئيس القسم"
--registrar-staff-id registrar1 --registrar-name "المسجل"
```

### ضمانات الإعداد

- السكربت **CLI فقط**؛ لا يوجد مسار HTTP عام للتسجيل أو الإعداد.
- يُكتب علامة `SystemSetting.key = initial_setup_completed` داخل **نفس المعاملة**
  التي تنشئ الحسابات، لذا:
  - إذا فشل أي جزء، تُلغى المعاملة كاملة ويبقى الإعداد قابلًا لإعادة المحاولة.
  - بعد النجاح، تُرفض أي محاولة ثانية برسالة تعارض (409).
- كل كلمة مرور يجب أن تكون **مستقلة** عن الأخريين، بطول 12–200 حرفًا، وتحتوي
  حرفًا كبيرًا وصغيرًا ورقمًا ورمزًا خاصًا، وألا تحتوي معرف الموظف.
- تُخزَّن كلمات المرور بـ bcrypt (تكلفة 12) فقط. لا تُطبع كلمات المرور إلا مرة
  واحدة في مخرجات الطرفية عند توليدها، ولا تُكتب في السجلات أو قاعدة البيانات
  بصيغة واضحة، ولا تُعاد في أي استجابة JSON.
- إذا وُجد **رئيس قسم وحيد** مسبقًا (كما في قاعدة البيانات الحية `head1`) يتم
  **تبنّيه** وتحديث كلمة مروره بدل حذفه أو إنشاء نسخة مكررة. وجود أكثر من رئيس
  قسم يوقف الإعداد حتى تُعالج الحالة يدويًا.
- لا ينشئ النظام أي حسابات إضافية تلقائيًا.

> **تنبيه للإنتاج:** تشغيل `setup:initial` على قاعدة البيانات الحية سيتبنّى
> `head1` ويستبدل كلمة مروره الحالية. نفّذ ذلك في نافذة صيانة مقصودة. تم تنفيذ
> هذا على PostgreSQL فعلًا عند الانتقال إليه (راجع `docs/POSTGRES_MIGRATION.md`).

## 2. تعطيل حساب المالك التجريبي

الحساب مستقل ولا يمكن للمقرر (ولا أي حساب عبر API) تعديله أو تعطيله أو إعادة
تعيين كلمة مروره. الطريقة الوحيدة هي الأمر المخصص:

```powershell
# تعطيل الحساب وإنهاء كل جلساته
pnpm --filter @attendance/api run staff:disable-owner

# إعادة تفعيله عند الحاجة للاختبار لاحقًا
pnpm --filter @attendance/api run staff:disable-owner -- --reactivate
```

كل عملية تُسجَّل في `AuditLog` بالإجراء `SYSTEM_OWNER_DISABLED` أو
`SYSTEM_OWNER_REACTIVATED`.

## 3. مصفوفة الصلاحيات

`HEAD_OF_DEPARTMENT` يحتفظ بجميع الصلاحيات كما كانت (لم تُحذف أي صلاحية).
أُضيفت `MANAGE_STAFF` إلى `REGISTRAR`، وأُنشئ دور داخلي `SYSTEM_OWNER` لا يُنشأ
عبر API.

| الإجراء | رئيس القسم | المقرر | محاضر | محاضر تقني | المالك التجريبي |
| --- | --- | --- | --- | --- | --- |
| إنشاء محاضر / محاضر تقني | نعم | نعم | لا | لا | نعم |
| إنشاء رئيس قسم | نعم | **لا** | لا | لا | نعم |
| إنشاء مقرر آخر | نعم | **لا** | لا | لا | نعم |
| إنشاء `SYSTEM_OWNER` | **لا** | **لا** | لا | لا | **لا** |
| تعديل اسم/معرف محاضر أو محاضر تقني | نعم | نعم | لا | لا | نعم |
| تعديل رئيس قسم أو مقرر آخر | نعم | **لا** | لا | لا | نعم |
| تعطيل/تفعيل محاضر أو محاضر تقني | نعم | نعم | لا | لا | نعم |
| تعطيل/تفعيل رئيس قسم | نعم (مع قاعدة آخر رئيس) | **لا** | لا | لا | نعم (مع القاعدة) |
| تعطيل/تفعيل حساب المالك | **لا** عبر API | **لا** | لا | لا | **لا** عبر API |
| إعادة تعيين كلمة مرور محاضر/تقني | نعم | نعم | لا | لا | نعم |
| إعادة تعيين كلمة مرور رئيس/مقرر | نعم | **لا** | لا | لا | نعم |
| عرض قائمة الموظفين | الكل | المحاضرون والتقنيون فقط | لا | لا | الكل |

### قواعد خادم إضافية

- كل مسارات `/api/staff` تتطلب جلسة صالحة وصلاحية `MANAGE_STAFF`.
- يمنع `StaffService` المقرر من استهداف أي دور خارج
  `LECTURER` و`TECHNICAL_LECTURER`، حتى لو عدّل الطلب يدويًا.
- لا يمكن للمقرر ترقية نفسه أو غيره إلى `HEAD_OF_DEPARTMENT` أو `REGISTRAR`.
- حساب `SYSTEM_OWNER` غير قابل للإدارة عبر API لأي دور.
- تعطيل أي حساب يلغي جلساته النشطة فورًا.
- إعادة تعيين كلمة المرور تلغي كل جلسات الحساب المستهدف.
- لا يوجد مسار حذف نهائي للموظفين؛ التعطيل يحافظ على ارتباطات المحاضرات
  وسجل التدقيق.
- يُمنع تعطيل **آخر رئيس قسم فعّال** أو إزالة دوره (HTTP 409).
- يُمنع تعطيل المستخدم لحسابه الحالي (HTTP 400).
- المعرفات مكررة؟ تُرفض بـ HTTP 409 قبل الوصول لقيد قاعدة البيانات.
- جميع الاستجابات تُخفي `passwordHash`.

## 4. واجهات إدارة الموظفين

| الطريقة | المسار | الوظيفة |
| --- | --- | --- |
| `GET` | `/api/staff` | قائمة الموظفين وحالتهم |
| `POST` | `/api/staff` | إنشاء حساب موظف |
| `PATCH` | `/api/staff/:id` | تعديل الاسم/المعرف/الدور |
| `PATCH` | `/api/staff/:id/status` | تعطيل أو تفعيل |
| `PATCH` | `/api/staff/:id/password` | إعادة تعيين كلمة المرور |

مثال إنشاء محاضر:

```json
POST /api/staff
{
  "staffId": "lecturer2",
  "fullName": "اسم المحاضر",
  "role": "LECTURER",
  "password": "Strong-Pass-123!"
}
```

## 5. سجل التدقيق

تُسجَّل العمليات التالية في `AuditLog`:

- `SYSTEM_INITIAL_SETUP`
- `STAFF_CREATED`
- `STAFF_UPDATED`
- `STAFF_DEACTIVATED`
- `STAFF_REACTIVATED`
- `STAFF_PASSWORD_RESET`
- `SYSTEM_OWNER_DISABLED`
- `SYSTEM_OWNER_REACTIVATED`

التفاصيل تحتوي معرف الموظف ودوره وأسماء الحقول المتغيرة فقط، ولا تحتوي أي كلمة
مرور.

## 6. الترحيلات

### PostgreSQL (قاعدة التشغيل الحالية)

- `apps/api/prisma/schema.prisma` + `apps/api/prisma/migrations/`
  (0001_init، 0002_online_foundation، 0003_staff_management) — **مُطبَّقة**
  عبر `prisma migrate deploy`.
- بيانات SQLite القديمة نُقلت مرة واحدة بمحتويات متطابقة، ثم أُزيلت أدوات
  التحويل القديمة بعد التحقق (تبقى في تاريخ Git عند الحاجة).

### SQLite (أُزيلت بالكامل)

- المخطط القديم وعميله وأدوات الترحيل وملفات البيانات الأرشيفية
  (`apps/api/prisma/attendance.db` و`backups/*.db`) أُزيلت من المشروع أثناء
  التنظيف بعد موافقة صريحة.
- النسخ الاحتياطية الحالية هي نسخ PostgreSQL التي تُنشئها
  `scripts/backup/backup-postgres.ps1`.

## 8. قرارات ومخاطر — الحالة النهائية

1. **دور `SYSTEM_OWNER` داخلي:** أُضيف إلى مصفوفة الأدوار لكنه لا يظهر في واجهة
   إنشاء الموظفين ولا يمكن إنشاؤه عبر API. **تمت الموافقة عليه.**
2. **حساب المالك غير قابل للإدارة عبر API:** حتى رئيس القسم لا يستطيع تعطيله أو
   تعديله عبر الواجهة؛ التعطيل عبر CLI فقط. **تمت الموافقة عليه.**
3. **تبنّي `head1`:** تم تنفيذ الإعداد فعلًا على PostgreSQL مع كلمة مرور
   جديدة لـ `head1` وسحب جلساته القديمة (تمت الموافقة عليه).
4. **حدود تسجيل الدخول قابلة للضبط** عبر متغيرات البيئة مع الإبقاء على
   القيم الافتراضية (10 محاولات/IP/5 دقائق، وقفل 5 محاولات/15 دقيقة).
5. **PostgreSQL:** تم الانتقال إليه عمليًا؛ راجع `docs/POSTGRES_MIGRATION.md`.
